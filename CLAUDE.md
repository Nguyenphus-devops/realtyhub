# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Three independent npm projects, no workspace/monorepo tooling. Always `cd` into one before running commands.

- `backend/` — NestJS 11 API (TypeScript, MongoDB via TypeORM `MongoRepository`)
- `admin/` — Next.js 16 App Router admin panel (React 19, Tailwind 4, TanStack Query)
- `web/` — Next.js 16 public site, same stack; own design tokens, no auth guard

The product is "X-Gym" (Vietnamese gym/dance business site). Comments, README docs, and user-facing strings are largely Vietnamese — match that when editing existing files.

## Commands

### backend/
```bash
npm run dev          # nest start --watch, NODE_ENV=development
npm run build        # nest build -> dist/
npm run start:prod   # node dist/main, NODE_ENV=production
npm run lint         # eslint --fix over {src,apps,libs,test}/**/*.ts
npm run format       # prettier --write
```
There is **no `test` script** and no `*.spec.ts` files, though a Jest config block lives in `package.json` (rootDir `src`, testRegex `.*\.spec\.ts$`). To run a single test after adding one: `npx jest src/path/to/file.spec.ts`.

### admin/ and web/
```bash
npm run dev          # admin: port 3001 · web: port 3000
npm run build        # next build
npm run start        # next start
npm run lint         # eslint
```
`admin` throws at config-load time if `NEXT_PUBLIC_API_URL` is unset (see `next.config.ts` and `src/config/apiRoutes.ts`) — no build or dev server starts without it. `web` does not yet require it, since it runs on mock data.

### Deployment
Each project has `deploy.sh` (rsync to `vps-prod`, then `npm install && npm run build && pm2 restart`) and an `ecosystem.config.js`. PM2 app names: `xgym-backend` (port 8011), `xgym-admin` (port 5011). `firstdeploy.sh` does the initial `pm2 start`.

## Environment

Env files are committed per-environment and selected by `NODE_ENV`:
- backend `ConfigModule` loads `.env.${NODE_ENV}` then `.env` — so `.env.development` / `.env.production`.
- Ports differ between files: `.env.development` uses **8010**, `.env.example`/pm2 use **8011**. `admin/.env.development` points at `http://localhost:8010/v1`. Check which one is live before assuming.

## Backend architecture

### Request pipeline (`src/main.ts`)
Global, applied in order: `AllExceptionsFilter` + `HttpExceptionFilter`, cookie-parser, helmet, then interceptors `LoggingInterceptor → MetricsInterceptor → TimeoutInterceptor → TransformInterceptor`, CORS (origins from `ALLOWED_ORIGINS`), morgan, 10 MB body limit, static serving of `MEDIA_LOCAL_DIR` (default `uploads/`), URI versioning with `defaultVersion: '1'`, and a strict `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`).

Consequences worth remembering:
- **Every route is under `/v1/...`.** The global `api` prefix is commented out in `main.ts`, so URLs are `http://host:8010/v1/blog`, not `/api/v1/blog`.
- **Every response is wrapped** by `TransformInterceptor` into `{ success, statusCode, message, timestamp, path, data }` (`src/common/interfaces/api-response.interface.ts`). Controllers return bare payloads; the interceptor skips `StreamableFile` and already-wrapped objects. The admin app unwraps with `unwrapApiData()`.
- `forbidNonWhitelisted` means any request body field missing from the DTO is a 400. Adding a field to the frontend requires adding it to the DTO.

### Global guards (`app.module.ts`)
Registered as `APP_GUARD` in order: `JwtAuthGuard` → `PermissionsGuard` → `ThrottlerGuard`. Both auth guards are opt-**out**, so a new controller is locked down by default:
- `@Public()` (`src/common/decorators/public.decorator.ts`) skips JWT auth.
- `@SkipPermissions()` skips the RBAC check.
- Public endpoints need **both** decorators (see `blog.controller.ts` for the pattern).

`JwtAuthGuard` resolves the token from cookie `token` first, then `Authorization: Bearer`, then a query param.

### Permissions (RBAC)
`src/modules/permissions/` — read its `README.md` (Vietnamese) for the full model. A permission is `{ resourceType, action, resourceTarget, effect }`; DENY beats ALLOW. Roles `SUPER_ADMIN`/`ADMIN` get a wildcard ANY/ANY/ANY permission; `STAFF`/`USER` get narrow sets generated by `generateGlobalPermissions()` in `permissions.helpers.ts` — permissions are **derived from role at request time**, not stored per user. `PermissionsCacheService` caches per-user results in memory and must be invalidated when a role changes.

Protect a route with `@RequiresPermission(PermissionResource.X, PermissionAction.Y, target)`, where target is `PermissionResourceTarget.ANY` or `GetResourceIdFromParams` for per-resource checks. `RolesService.onModuleInit()` seeds default roles on boot.

### Module conventions
Each `src/modules/<name>/` follows: `<name>.module.ts`, `<name>.controller.ts`, `<name>.service.ts`, `<name>.ts`, `dto/` or `dtos/`, `entities/`.

The bare `<name>.ts` file is the module's **contract file** — it holds the `I<Name>Service` interface plus shared types (`PaginatedX`, `RequestUser`, action constants). Services `implements` these interfaces. Cross-module injection goes through the `Services` enum tokens in `src/common/utils/constants.ts` (e.g. `@Inject(Services.ROLES) private rolesService: IRolesService`) rather than the concrete class, so update the interface when changing a public service method.

Controller paths come from the `Routes` enum in the same constants file — `@Controller(Routes.BLOG)`. Add new routes there.

### Data layer
`DatabaseModule` registers **both** Mongoose and TypeORM-for-Mongo, but nothing uses Mongoose (`@InjectModel` appears nowhere). All persistence is TypeORM: `@Entity()` classes extending `EntityHelper` with `@ObjectIdColumn() _id`, injected as `MongoRepository<T>` / `Repository<T>`. `synchronize` and `autoIndex` are on outside production.

`HistoryService` is the shared audit trail — services inject it and log with the `HISTORY_ACTIONS` constants from `src/modules/history/history.ts`. Add a constant there when adding an audited operation.

Uploads are written to the local filesystem under `uploads/images/YYYY/MM/DD/` (`ImagesService.buildUploadFolderByDate`); `@aws-sdk/client-s3` is a dependency but the active path is local (`ADDRESS_UPLOAD=local`). Video uploads stream progress through `VideoProgressService`, an in-memory `Map<uploadId, Subject<UploadProgressEvent>>` consumed via SSE.

`@nestjs/swagger` decorators (`@ApiBearerAuth`) are used, but `SwaggerModule` is never set up in `main.ts` — there is no `/docs` endpoint.

## Admin architecture

### Routing
App Router with two route groups: `app/(admin)/` (dashboard, wrapped in `AppSidebar`/`AppHeader` chrome) and `app/(auth)/`. Route folders mirror backend resources (`blog`, `banner`, `leads`, `users`, …) and mostly just render a component from `src/modules/`.

### Feature modules
`src/modules/<feature>/` = `components/` + `hooks/` + `models/` + `services/`. The data flow is fixed:

`apiRoutes.ts` (URL builders) → `services/*.service.ts` (axios via `@/config/api`, unwrapped with `unwrapApiData`) → `hooks/use*.ts` (TanStack Query `useQuery`/`useMutation` with explicit `queryKey`s) → `components/*.tsx`.

Never call axios directly from a component; add the route to `apiRoutes.ts` and go through the service+hook layers.

### Auth
`app/layout.tsx` is a server component: it reads the `token` cookie, calls `GET /auth/status` server-side, and seeds `AuthProvider` with `initialUser`/tokens so the first paint isn't unauthenticated. Provider nesting is `AuthProvider → PermissionsProvider → AdminGuard → QueryProvider → SidebarProvider`.

`src/config/api.ts` is the single axios instance: attaches `Authorization` from `localStorage.token`, and on a 401 runs a **single shared refresh promise** against `/auth/refresh`, retrying the original request once (`_retry` flag). Public auth endpoints are excluded from refresh. Tokens live in both cookies (set by the backend) and `localStorage`.

`AdminGuard` only reacts to `isAuthReady` from `AuthContext` — `AuthProvider` is the sole owner of session verification, so don't add verify/refresh calls in guards or pages. `PermissionsContext` mirrors the backend permission model client-side (`hasPermission`/`canCreate`/`canEdit`/…) for hiding UI; it is not a security boundary.

### Path alias
`@/*` → `admin/src/*`. Note `app/` is a sibling of `src/`, not inside it.

## Web architecture (public site)

Same layering as `admin/` (`models → services → hooks → components → route`) and
the same `@/*` → `src/*` alias, but deliberately simpler: no auth, no guard, no
axios instance yet. Differences worth knowing:

- Its own design tokens in `web/app/globals.css` — a blue/navy/orange palette,
  unrelated to admin's TailAdmin theme. Shared idea, not shared file.
- `src/common/components/PlaceholderThumb.tsx` renders a deterministic gradient
  from a seed string, so no image assets are needed until real ones exist. Pass
  `src` and it renders an `<img>` instead.
- Vietnamese route names (`/du-an`); `/` currently redirects there because the
  home page is not built.
- `ProjectService` is the only file that knows data comes from mocks. Keep it
  that way — no component or hook may import from `mocks/`.

## Project direction

The codebase is being rebuilt from the current X-Gym CMS into a **Vietnamese
real-estate sales platform** (dự án, chủ đầu tư, khu vực, loại hình, căn hộ,
so sánh, tin tức). The existing gym modules stay as the reference implementation
of the repo's conventions — see the `realestate-domain` skill for the target
model and build order.

`web/` is the newest app and currently runs on **mock data**: the project list
page and the project detail page (`/du-an/[slug]`, 11 tabs) are complete
UI-side, both backed by `web/src/modules/project/services/project.service.ts`,
which reads from `mocks/` behind an API-shaped interface. When the backend
`projects` endpoints land, only that one file changes.

Detail-page specifics: `models/project-detail.model.ts` is the contract for all
11 tabs; the active tab lives in `?tab=`. The bảng hàng (`quy-can`) is a
**separate paginated call** (`ProjectService.units`), not part of `ProjectDetail`,
because one project can hold hundreds of units. The route server-reads the
project and passes it to the client component as `initialData`, so the detail
HTML is server-rendered for SEO.
